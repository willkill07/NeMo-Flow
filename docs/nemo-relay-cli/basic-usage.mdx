NeMo Relay uses one persistent coding-agent proxy for each enrolled OS user.
Install an agent once, then start it normally from its CLI, GUI, cron job, API
server, or other supported local mode.

## Enroll an Agent

```bash
nemo-relay install codex
# Linux only: export CODEX_CA_CERTIFICATE="<path printed by install>"
nemo-relay doctor codex
```

The first enrollment:

- Selects an available `127.0.0.1` port for the current user and persists it.
- Creates a constrained per-user CA. macOS installs it in the login Keychain,
  Windows installs it in CurrentUser Root, and Linux writes only agent-scoped
  CA bundles without changing system trust. On Linux, Codex prefers
  `CODEX_CA_CERTIFICATE`. If that variable is unset, Relay accepts
  `SSL_CERT_FILE` only when the selected bundle contains the active Relay root.
  The installer-printed `CODEX_CA_CERTIFICATE` value is the recommended
  selection.
- Registers the `nemo-relay-agent-proxy` user service.
- Creates an agent-specific proxy credential.
- Captures the agent's existing corporate proxy route and custom CA.
- Patches only the selected agent and installs trusted lifecycle hooks.

The selected port is intentionally dynamic. Do not copy a port from another
user or installation into configuration. Agent settings and hooks discover the
endpoint from protected enrollment state.

Installing another agent adds an independent credential and settings ownership
record to the same user service:

```bash
nemo-relay install claude-code
nemo-relay install hermes
```

`nemo-relay install all` enrolls supported CLI agents discovered on `PATH`.
Claude Desktop remains an explicit preview enrollment and is never inferred by
`all`.

## Configuration

The proxy loads Relay system and user configuration. Coding-agent project
`.nemo-relay` configuration is not loaded, and project-specific transparent
runs have been removed. Enrollment stores the absolute user configuration
directory in protected proxy state, so the login service reads the same files
even when its service manager does not inherit `XDG_CONFIG_HOME` or the
installer shell environment. Changing the user configuration root requires a
clean uninstall and reinstall.

Provider authorization normally arrives in the enrolled client's native OAuth
or API-key request. For a durable fallback, put `openai_auth_header` or
`anthropic_auth_header` under `[upstream]` in the user `config.toml`. Relay
rejects these secrets in system configuration, symlinked files, and user
configuration whose file or parent directory is accessible to another user.
The persistent service never reads provider keys from its process environment.
Standard provider credentials in a client request take precedence. A configured
OpenAI header is also an explicit API-key replacement for Codex ChatGPT OAuth,
so it selects the native OpenAI API route instead of the ChatGPT backend.

Use the policy editor for the user layer, or add `--system` for the system
layer:

```bash
nemo-relay config
nemo-relay config --system
```

The managed provider engine applies the configured request guardrails, request
interceptors, execution interceptors, streaming collectors, finalizers, and
exporters.

## Provider Routing

Relay intercepts only these initial native hosts:

| Agent credential | Managed hosts |
| --- | --- |
| Claude Code/Desktop | `api.anthropic.com` |
| Codex | `api.openai.com`, `chatgpt.com` |
| Hermes | All three native hosts |

Claude and Codex credentials reject every destination outside their managed
host sets. Unknown Hermes providers are the one managed-inference exception:
Relay tunnels eligible public HTTPS destinations reached with `CONNECT` on
port 443 without certificate generation and marks their hook events
`hook_only_degraded`. Invalid HTTP, alternate-port, credential-bearing,
private, loopback, link-local, multicast, reserved, or
managed-native-path traffic still fails closed.

For intercepted traffic, the `CONNECT` authority, TLS SNI, HTTP `Host`, agent
credential, method, and provider path must agree. A mismatch fails closed.

## HTTP, SSE, and WebSockets

Claude and supported Hermes native providers use authenticated `CONNECT` with
exact-host TLS interception. Codex uses a generated provider alias that points
directly to the same listener and supports:

- OpenAI Responses HTTP.
- OpenAI Responses SSE.
- OpenAI Responses WebSockets.

Every Codex WebSocket text `response.create` is one managed streaming call.
Relay rewrites it through the OpenAI Responses codec and middleware, forwards
events in provider order, and finalizes on a terminal event, failure, timeout,
or disconnect. Only one response can be active on a connection. Binary or
malformed frames are rejected.

## Lifecycle Hooks

Installed hooks invoke the internal `hook-forward` transport. Before delivery,
it verifies:

- The agent-specific enrollment.
- Service identity and health.
- Service generation.
- Settings fingerprint.
- Payload size.

Identity, generation, settings, or delivery failures return a blocking exit
status. Relay sends each hook payload once and does not retry after transmission
starts.

## Corporate Proxies

Enrollment reads explicit HTTP(S) proxy, Basic authentication, custom CA, and
`NO_PROXY` values from the agent's owned configuration where available and
from the installer environment. It does not discover OS/GUI proxy settings,
PAC/autodiscovery, SOCKS, NTLM, Kerberos, or platform-integrated proxy
authentication. Set the intended explicit proxy environment while enrolling.

Relay resolves each provider hostname locally, rejects the route unless every
answer is public, and sends the validated IP-literal authority to an upstream
corporate proxy. Corporate proxies that require hostname ACLs or proxy-side
DNS resolution must allow this behavior or the route fails closed.

The custom-CA aliases are `REQUESTS_CA_BUNDLE`, `SSL_CERT_FILE`,
`NODE_EXTRA_CA_CERTS`, and `AWS_CA_BUNDLE`. Relay reads applicable agent-owned
values before the installer environment, requires absolute paths that resolve
to regular files, and permits multiple aliases only when they canonicalize to
the same file. Claude settings, the Hermes environment, and installer-time
Codex or ambient values therefore cannot silently select conflicting bundles.

Codex and Hermes retain independent routes. Claude Code and Claude Desktop
share `~/.claude/settings.json`; when both are enrolled, provider traffic uses
one active shared Claude credential and corporate route. Their ownership
records remain separate, but provider-traffic attribution between those two
processes is not reliable.

Relay removes bypasses that would skip its own loopback or managed native
hosts. It also removes CIDR exclusions because provider addresses can change
and an offline enrollment cannot prove that a network excludes every managed
provider address. It preserves other pre-existing Hermes hostname and literal
`NO_PROXY` exclusions in both case variants and restores the exact original
values on uninstall. Doctor reports higher-precedence ambient Hermes proxy
settings that can conflict with the enrolled `$HERMES_HOME` environment. Bare
IPv6 exclusions are supported; IPv6 entries that include a port must use
bracket syntax, for example `[2606:4700:4700::1111]:443`.

## Diagnose the Installation

```bash
nemo-relay doctor codex
```

Doctor checks the discovered endpoint, service executable and generation,
configuration fingerprint, trust fingerprint, signer, cached certificates,
agent settings, hooks, and upstream proxy. It reports endpoints without
printing enrollment tokens or proxy passwords.

Stopping the user service causes managed provider requests and installed hooks
to fail closed. Restart it through the platform user-service manager or repair
the enrollment with a force install after stopping the affected agents:

```bash
nemo-relay install codex --force
```

## Remove an Enrollment

```bash
nemo-relay uninstall codex
```

Relay restores only its owned Codex fields. Other enrolled agents remain
active. Removing the final enrollment also stops the user service, removes the
exact macOS/Windows current-user CA trust or Linux agent-scoped CA bundles,
deletes its signing key and certificate cache, and removes shared state. On
Linux, apply the Codex uninstall message to remove the Relay-managed
`CODEX_CA_CERTIFICATE` launch value and restore any recorded pre-enrollment CA
selection before restarting Codex.

## Security Boundary

The integration protects against accidental bypass, stale configuration, and
service failure. It is not tamper-resistant enforcement against a local user
who deliberately removes their own hooks, trust, or proxy settings.

On macOS and Windows, Relay keeps the CA signing key non-exportable in the
platform user key service. Linux stores the PKCS#8 signing key in an owner-only
file because supported distributions do not provide one consistent
non-exportable user signing service. Compromise of the trusted signer can
impersonate the managed provider hosts covered by its name constraints.
Linux's owner-readable file-backed key is the largest residual signer risk.
Non-exportable macOS and Windows keys reduce key extraction but do not protect
against malicious code already executing as the enrolled OS user and invoking
that user's signer.

## Operational Limits

The default hook body limit is 20 MiB and the default HTTP passthrough body
limit is 100 MiB. Configure them in system or user `config.toml` and refresh
each enrollment with `nemo-relay install <agent> --force`:

```toml
[gateway]
max_hook_payload_bytes = 20971520
max_passthrough_body_bytes = 104857600
```

Codex WebSockets use an 8 MiB frame limit, a 16 MiB write-buffer limit, at most
32 concurrent sockets, a 120-second idle timeout, and a 30-minute response
timeout. These WebSocket limits and the proxy's 256-connection ceiling are
currently fixed compatibility limits. WebSocket-slot exhaustion returns a
service-unavailable response. Listener-capacity exhaustion accepts and
immediately closes the excess TCP connection without an HTTP response.
Oversized HTTP or hook bodies return a payload-too-large error, and protocol
violations close the WebSocket.
